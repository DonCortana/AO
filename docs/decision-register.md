# Atlas Decision Register

Append-only. A decision is added here, never edited after acceptance — a
reversal is a new decision that references the one it retires. Execution
Plan Technical Lane step 1 requires this file exist in the repo alongside
the methodology, operating system and execution plan.

Per Methodology §10 (Governing Rule): "No methodology version becomes
client-active from convenience, provider deprecation or software limitation
alone. The decision is documented first, then implemented, then applied
forward." Decisions are documented before implementation; any exception is
noted in the row itself.

| D-036 | 2026-08-27 | The set of eligible platforms is a required explicit argument to AVS computation, with no default and no inference from the observations present. Reason: Methodology §4.3 defines AVS as the mean PlatformScore "across eligible calibrated platforms", and §8.4 makes eligibility the *output* of a calibration gate (raw mention agreement >=80% and Cohen kappa >=0.60, or >=85% plus documented manual review) that has not been run — it is roadmap Week 5 — and no schema column anywhere records per-platform eligibility. Defaulting to "every platform present in the data" would silently fold uncalibrated, evidence-only platforms into a client-facing AVS, which §8.4 forbids ("A platform failing the gate remains evidence-only and is excluded from AVS"). Requiring the caller to name the eligible set makes that a deliberate, auditable act. | D-037 | 2026-08-27 | The §6.2 hierarchical paired bootstrap is implemented on the standard library's `random.Random` (Mersenne Twister) with a caller-supplied seed that is required, not optional, and is returned with the result for storage alongside the score row. No numpy, scipy or statsmodels dependency is added. Reason: a client-facing interval must be exactly reproducible from stored inputs (§9 requires every score row carry its interval bounds and evidence references; §8.4 freezes v1.0 only once "the score engine reproduces hand calculations"). `random.Random` is documented as reproducible across Python versions for a given seed, whereas numpy's `Generator` stream is explicitly not guaranteed stable across releases. Performance was measured rather than assumed and does not force a tradeoff: 10,000 resamples over 40 prompts x 4 platforms x 5 replicates completes in 1.6 s in pure Python (3.3 s at 80 prompts). The 2.5th/97.5th percentiles use linear interpolation between closest ranks, verified against `numpy.percentile(..., method="linear")` to 7.1e-15 over 200 random arrays x 5 quantiles. The Wilson interval used for Mention Rate and Top-3 Rate is likewise hand-implemented, verified against `statsmodels.stats.proportion.proportion_confint(method="wilson")` to 1.1e-16 across 19 cases including the 0/n, n/n and n=1 boundaries; z is pinned to 1.959963984540054 rather than 1.96 (a ~6e-6 difference on the bound) so it is exactly the standard normal 0.975 quantile. | Active |
| D-038 | 2026-08-27 | Methodology §6.2 specifies the hierarchical paired bootstrap in one sentence that is under-determined in four ways, each of which changes the reported interval. Resolved before implementation. (a) **What is paired:** one prompt-ID draw is made per resample and applied to *both* periods, which is what "Baseline and validation are recomputed within the same bootstrap draw" requires; replicate observations are then resampled independently within each period, because replicate 3 of a baseline run and replicate 3 of a validation run are not the same unit and pairing them would be fiction. This is load-bearing and was measured by controlled A/B against the shipped implementation — identical data, identical seed, 10,000 resamples, the *only* difference being whether one prompt draw feeds both periods (`movement.py:199-208`) or each period draws independently. Median 95% CI width at 40 prompts x 4 platforms x 5 replicates: **4.93 AVS points paired vs 15.82 unpaired, a 3.2x inflation**; the ratio holds across scales (2.4x at 12 prompts, 2.9x at 20, 3.3x at 80). On one representative cycle the paired interval is (+4.62, +9.61), which excludes 0 and returns Improvement, while the unpaired interval on the same data is (-1.12, +15.31), which includes 0 and can only return Inconclusive — so the choice decides whether an MRC-5.0 movement is reportable at all. (An earlier uncontrolled estimate put the unpaired width near 26 points; it came from a diagnostic that also varied tier count and the pairing of the underlying data, and is superseded by the A/B figures above.) (b) **Repeated prompts:** a prompt drawn k times in one resample gets k independent replicate resamples, the standard hierarchical treatment. (c) **Empty cells:** a prompt-platform cell holding no scoreable replicate in a given draw is dropped from that PlatformScore's intent-weighted mean and its weight removed from the denominator, rather than imputed as zero — a technical or parsing gap is never scored as an absence (Operating System §1). (d) **Unpaired prompts:** the resampling frame is the intersection of prompts observed in both periods; a prompt present in only one period cannot contribute to a paired delta, is excluded from the frame, and is reported in the result so the exclusion is visible rather than silent. Additionally the reported point-estimate delta is computed from the observed data, not taken as the mean of the bootstrap distribution, and "95% CI excludes 0" is evaluated strictly (a bound of exactly 0.0 includes 0, so the verdict is Inconclusive). Interval calibration was checked by simulation against a known population delta: 98.0% coverage at a nominal 95% over 300 simulated cycles — slightly conservative, the safe direction for a reporting threshold. | Active |
| D-039 | 2026-08-27 | "Observation completeness" — the input to §6.2's Incomplete verdict and to Operating System §11's "cycle completeness below 90% produces Incomplete status" — is defined as scoreable observations divided by planned observations for the run plan, evaluated separately for baseline and validation, with the movement verdict requiring *both* periods to reach 90% and reporting the lower of the two. Reason: the 90% threshold is stated in three documents and its denominator in none, and the choice decides whether a cycle publishes a verdict at all. An observation counts as scoreable only if its status is `complete`, its grounding is not `ungrounded_ineligible` (§8.1 marks those ineligible rather than scoring them), and it carries at least one recommendation row (per D-034 an unparsed observation is incomplete, not absent). The denominator comes from the run plan's own task list, which the planner writes before any provider call (Technical Lane step 3), so it is fixed in advance and cannot shrink to flatter the ratio. Taking the lower of the two periods rather than a pooled figure prevents a well-covered baseline from masking a thin validation run, which is the case the gate exists to catch. | Active |
| D-040 | 2026-08-27 | The score bands in §3.1 (ARS: Fragile 0-39, Developing 40-59, Established 60-74, Strong 75-89, Advanced 90-100) and §4.4 (AVS: Not observed 0-9, Detectable 10-24, Emerging 25-44, Established 45-64, Strong 65-84, Leading 85-100) are printed as integer ranges, but both scores are continuous — ARS is a weighted mean over 70 and AVS is 100 x a mean of means — so values such as 39.5 or 84.7 fall in the gaps between the printed ranges. Bands are therefore evaluated as half-open intervals whose upper edge is the next band's printed lower bound: ARS [0,40) Fragile, [40,60) Developing, [60,75) Established, [75,90) Strong, [90,100] Advanced; AVS [0,10) Not observed, [10,25) Detectable, [25,45) Emerging, [45,65) Established, [65,85) Strong, [85,100] Leading. Chosen over rounding to the nearest integer first, because rounding would lift a 39.5 ARS into Developing and make a client-facing band label depend on a display convention rather than on the score itself. Settled before any report renders a band. | Active |
| D-041 | 2026-08-27 | A positive recommendation at rank 11 or beyond scores RPV 0.00. Reason: Methodology §4.1 tabulates RPV for ranks 1, 2, 3, 4-5 and 6-10 and then simply stops, so a venue recommended in position 11+ has no tabulated value and the lookup had to do *something*. Rejected extrapolating the decay curve past rank 10, which would invent a band the methodology never wrote and put a number in a client report that no document supports. Rejected raising an error, which would let one long list from one provider block an entire cycle's score. 0.00 is the reading most consistent with the table's own trajectory (1.00 -> 0.80 -> 0.65 -> 0.45 -> 0.25, already at the floor of usefulness by rank 6-10) and with §4.1's principle that only meaningful positive recommendations raise AVS. Such a replicate remains `ranked` and scoreable, so it is distinct from `absent` in the evidence trail even though both score 0.00. Revisit if real observations show providers routinely returning lists deep enough for this to bite; the honest fix would be a §4.1 amendment extending the table, not a code change. | Active |

## Adding a decision

1. Determine version treatment per Methodology §10 (patch/clarification vs.
   new baseline vs. major methodology version vs. operating update).
2. Add a row here with the next sequential D-xxx ID, dated, with the
   decision stated in full — not just a reference to a discussion.
3. Only then implement it in the methodology/operating docs and/or code.
4. If the decision retires an earlier one, mark the earlier row's Status
   column "Retired by D-xxx" — do not delete or rewrite it.
